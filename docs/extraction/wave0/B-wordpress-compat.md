## 1. Headline

1. **Newest-copy-wins does not hold for Composer-bundled copies today. Whichever copy loads first wins.** Composer includes an `autoload.files` entry only once per process. The key is `md5(package-name . ':' . path)`, stored in `$GLOBALS['__composer_autoload_files']` (`vendor/composer/autoload_real.php:37-45`). Every bundled copy of `tangible/ddd` has the same identifier, `e354914457af2735a61959cdb08105cf` (`vendor/composer/autoload_static.php:19`, and the same hash in `tangible-cred:vendor/composer/autoload_static.php:16`). The second vendor tree's `tangible-ddd.php` never runs, so it never registers. Measured with real `composer install` fixtures: load order A(0.6.5),B(0.6.6) registered only `["0.6.5"]` and the winner was 0.6.5. Order C(0.2.5),B(0.6.6) made the winner "0.2.4". Requiring each copy's loader file directly (bypassing the Composer dedup) restored newest-wins. Two things follow. The 0.6.x hotfix reaches a site only if its plugin's vendor happens to load first, or if `tangible-ddd` is activated as a plugin. A new `ddd-wp` distribution also cannot rely on `autoload.files` as it stands. The docs claim otherwise (`docs/wiring-a-consumer.md:42-44`, `README.md:64`).
2. **Releases 0.2.5 through 0.5.2 register under the literal version `'0.2.4'`** (`v0.2.5:tangible-ddd.php:233,240,395`; the same holds for v0.3.0, v0.4.0 and v0.5.2). This was fixed in 0.6.0 (`559b172`). A site running reporting (`^0.2.5`) cannot tell 0.2.4 from 0.5.2. Any 0.6+ or new copy still wins over them on version order.
3. **The new WP line has to join the existing `Tangible_DDD_Versions` registry, with the same class name, API and hook priorities.** A second registry would produce two winners. Both would `require_once` their own `ddd-wordpress/hooks.php`, and the procedural functions are declared without `function_exists` guards (for example `ddd-wordpress/hooks.php:32`), so the site fatals with "Cannot redeclare".
4. **Whichever copy loads first also supplies the shared-named functions**, including `tangible_ddd_self_consume` (`tangible-ddd.php:353-389`). That function hard-codes `require_once $winner['path'] . '/ddd-wordpress/self/index.php'` (`:372`). A failed `require_once` is an uncatchable fatal, so the `try` around it does not help. The new winner's registered path must therefore contain `ddd-wordpress/self/index.php`, and the files that index requires, or a site with a legacy copy loaded first white-screens at `plugins_loaded:20`.
5. **Legacy consumers compile their own containers from YAML that names framework classes, static factories and constructor shapes** (cred: 27 distinct `TangibleDDD\*` service IDs in `includes/di/*.yaml`; the scaffold template at `ddd-wordpress/cli/class-ddd-command.php:407-537`). They implement `IDDDConfig` themselves (`tangible-cred:src/Infra/Config.php:7`). Once the new line wins, all of this becomes a frozen ABI: class names, public constructor parameters and their order, `OutboxConfig::from_options`, the eight `IDDDConfig` methods, procedural functions, hook, option and AS names, table shapes and envelope keys. Section 5 lists the aliases and facades this needs.

Loader history that matters for compatibility:

- 0.1.x has no registry. Its `composer.json` autoload `files` lists `ddd-wordpress/*.php` directly (`v0.1.6:composer.json:28-35`), and `define('TANGIBLE_DDD_VERSION', ...)` is unguarded (`v0.1.6:tangible-ddd.php:22`). A 0.1.x copy next to any registry copy defines `TangibleDDD\WordPress\*` functions from its own files. The winner's `require_once` of different paths then redeclares them and the site fatals. This is unsupported today and cannot be fixed from the new side.
- 0.2.0 through 0.6.6 all use the registry. 0.2.5 through 0.5.2 identify as `'0.2.4'` (headline 2).

## 3. Load-order matrix

Actors:
- **L2**: a legacy 0.2.x/0.5.x monolith copy (identity `0.2.0-dev` or `0.2.4`), for example tangible-reporting `^0.2.5`.
- **L6**: a legacy 0.6.x monolith copy (0.6.0 through 0.6.6, plus the prepared 0.6.7 hotfix).
- **N**: the new distribution, ddd-core plus ddd-wp, assumed identity ≥ 0.7.0.
- **P**: `tangible-ddd` activated as a plugin, so its loader is included directly and bypasses the Composer dedup.
- **C**: a plugin that bundles ddd-core only, without ddd-wp.

## 5. Class aliases and facades N must provide

Principle (from spec line 106): an FQCN has exactly one owning package. When a class moves, the old FQCN stays as a `class_alias` or a thin facade in **ddd-wp**, never as a duplicate PSR-4 declaration. For N to win on a legacy site, these legacy names must resolve from N's paths (B7).

- **Must keep the exact FQCN and public constructor shape** (named in legacy YAML or scaffolds): `TangibleDDD\Application\Correlation\CorrelationMiddleware`, `Application\Persistence\TransactionMiddleware`, `Application\Events\{EventsUnitOfWork, EventRouter, DomainEventsPublishMiddleware, IDomainEventDispatcher, IIntegrationEventBus}`, `Application\Outbox\{OutboxConfig (+from_options), IOutboxPublisher}`, `Application\Process\{ProcessRunner, LongProcess}`, `Application\Logging\Redactor`, `Application\CQRS\{SelfExecutingCommandMiddleware, HandlerClassNameInflector}`, `Infra\{IDDDConfig, DDDConfig, Config, IOutboxRepository, IProcessRepository}`, `Infra\Persistence\{OutboxRepository, ProcessRepository, BehaviourWorkflowRepository, WorkItemRepository}`, `Infra\Services\{OutboxProcessor, OutboxIntegrationEventBus, ActionSchedulerOutboxPublisher, RoutingOutboxPublisher, WordPressEventDispatcher}`, `Infra\DependencyInjection\DDDCompilerPasses`, `Domain\Repositories\{IBehaviourWorkflowRepository, IWorkItemRepository}`, `Domain\DataRendering\NullValueRenderer`, `Domain\Shared\IValueRenderer`. Sources: `ddd-wordpress/di/services.yaml`, scaffold `class-ddd-command.php:407-605`, cred YAML.
- **Base classes and traits that consumers extend or use** (a signature change is a fatal at class load): cred uses about 70 `TangibleDDD\*` symbols, including `Application\EventHandlers\{WordPressActionHandler, IntegrationListener}`, `Application\BehaviourWorkflows\WorkflowHandler` (abstract `reschedule`, `ddd-src/Application/BehaviourWorkflows/WorkflowHandler.php:107`), `Domain\DataRendering\TangibleFieldsRenderer`, `Infra\Persistence\Shared\PersistsAggregatesRepository`, `Infra\Persistence\Select\QueryBuilderSelect`, `Infra\Exceptions\{LockingException, QueryException}`, `Application\Exceptions\ApplicationException`, `Application\CQRS\{CommandBusAware, QueryBusAware}`, `Application\Correlation\Correlation`. Where the spec moves one to WP (`WordPressActionHandler`, `TangibleFieldsRenderer`, `WPErrorException`), ddd-wp owns the old FQCN outright. It does not alias to itself: the class simply stays under its old name in ddd-wp's autoload map.
- **Procedural namespaces:** `TangibleDDD\WordPress\*` (14 files, `tangible-ddd.php:307-327`) and `TangibleDDD\WordPress\SelfConsumer\di()` (`ddd-wordpress/self/index.php:25-31`, used by `ddd-src/Application/Commands/Command.php:10,25`).
- **Global symbols:** `Tangible_DDD_Versions` (same API), `tangible_ddd_register_<slug>`, `tangible_ddd_initialize_<slug>`, `tangible_ddd_self_consume`, and the `TANGIBLE_DDD_VERSION` constant (defined only if absent).
- **Aliases already removed in 0.4.0** (`50fcd29`: "alias stubs die", for example `TangibleDDD\WordPress\ConsumerRegistry`, `v0.2.5:ddd-wordpress/ConsumerRegistry.php:1-10`). If 0.2.5 consumers are in the window, N may need to restore the 0.2.x aliases. The winner today is 0.6.x without them, so whether reporting-on-0.2.5 works on a 0.6.6 winner is already unverified.

## 6. Distribution requirements (so existing consumers keep working unchanged)

- **D-1 One registry, one layout.** N registers into `Tangible_DDD_Versions` at `plugins_loaded:0` with a version string > every 0.6.x hotfix (e.g. 0.7.0). Its registered path is a directory that contains the legacy layout the older shared symbols expect: `ddd-wordpress/self/index.php` and its YAML imports (B5, B6). An assembled distribution tree, or forwarding shims at those paths, satisfies this.
- **D-2 Version-unique loader entry.** The files-autoload entry must differ per release, for example `"files": ["loader/tangible-ddd-0_7_0.php"]`, so Composer's cross-vendor dedup never suppresses a newer copy. This applies to the new line and to the 0.6.7 hotfix branch (B1). Extend `LoaderIdentityTest` to assert that the files entry, the constant, the register literal and the function slugs all carry the same version. Existing deployed copies stay deduped among themselves; nothing fixes those except loading order or P.
- **D-3 Matched pair.** The ddd-wp initializer maps `TangibleDDD\` to its sibling ddd-core by path, captured in the closure, and verifies that the core's version file matches exactly before it initializes. It never uses whichever ddd-core Composer resolves (matrix #9).
- **D-4 Authoritative winner autoload.** For `TangibleDDD\*`, the winner resolves from its own paths plus a legacy alias map. It logs each fall-through and exposes the list as a diagnostic (dashboard or `wp ddd` health) (B7, matrix #13).
- **D-5 ABI freeze list.** Everything in section 5, plus hook, option and AS names (B15), AS arg shapes (B16), envelope keys (B17), table names and columns (B18, B19) and `install_tables(IDDDConfig)`. New constructor dependencies are optional and defaulted (B9). No new abstract methods on consumer-implemented interfaces (B11).
- **D-6 Schema discipline.** Additive migrations only, one shared ledger with the hotfix line, and uniqueness added in new tables (B18-B22).
- **D-7 No PDO in WP.** ddd-wp wires wpdb-backed ports. The pdo-default adapter (host-supplied connection plus schema SQL, per the operator decision) is never activated under WordPress (B24).
- **D-8 Core stays inert.** ddd-core's autoload has no `files` entry except pure function definitions (e.g. `ddd-src/Domain/Shared/assert.php`), no loader and no registry. On WordPress, core is always the winner's core (matrix #10).
- **D-9 Composer constraints.** Existing consumers stay on `^0.6.x` / `^0.2.5` (operator: no consumer dependency changes). Compatibility is therefore about coexisting on one site, not about upgrading a consumer's lockfile. Consumers that adopt N require `tangible/ddd-wp`, or `tangible/ddd` ≥0.7 if F-packaging's single-distribution recommendation is taken, in which case D-2 is mandatory (matrix #7).

## Open questions

1. Is tangible-reporting (`^0.2.5`, identity "0.2.4") inside the compatibility window? If it is, does it work on a 0.6.6 winner today? That is unverified, and the 0.4.0 alias purge suggests it may not. The local `tangible-reporting` master does not reference `tangible/ddd`, so the `^0.2.5` usage must be on another branch.
2. Does any consumer build rename or prefix vendor packages (Strauss, Mozart, the Tangible roller), or include `vendor/tangible/ddd/tangible-ddd.php` directly? Either would change B1 per consumer. cred does neither (`tangible-cred:tangible-cred.php:15`).
3. Is `tangible-ddd` activated as a plugin (P) on any production site? If so, the hotfix can reach sites through that copy regardless of B1.
4. Distribution shape: an assembled `tangible/ddd` ≥0.7 in the legacy layout (F-packaging), or `tangible/ddd-wp` plus shims at `ddd-wordpress/self/*`? Either way D-1 and D-2 hold. This decides who owns the assembly step.
5. For the 0.6.7 hotfix: ship D-2 (version-unique files entry) in the hotfix itself, so future 0.6.x copies stop deduping? The change is on the loader, a sensitive surface, and it cannot help copies already deployed.
6. B10 and B11 design choice: keep WP-flavoured static factories and the `IDDDConfig` shape on core FQCNs, delegating to host-registered providers, or move those FQCNs to ddd-wp and introduce new core names?
7. Should N's winner autoloader enforce authority (refuse fall-through for `TangibleDDD\*`) or only log and diagnose (B7)? Refusing breaks `class_exists` probes; logging leaves the mixture possible.
8. Multisite: `Infra\Config::for_wordpress()` captures the table prefix once (`ddd-src/Infra/Config.php:21-24`), unlike `DDDConfig::table()`. Preserve this as-is for the self-consumer, or fix it in N?
9. Is the brief lock-name change window (B21: prefixed process locks) acceptable, or should N take both the old and new lock names during one release?
10. Will the ignition uniqueness table (B22) scope by `blog_id`? That depends on whether multisite consumers share a prefix across blogs; the current `DDDConfig::table()` makes tables per-blog.

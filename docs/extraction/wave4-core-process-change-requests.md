## CR-W4P-1: D3 keyed awaits, routes, precheck, any-of, dynamic AwaitAll

- **`Application\Process\IAwaitKeyed { await_key(): ?string }`.** Implemented by facts that answer keyed awaits (a job report carries the job id the process minted).
- **`Runtime\Process\AwaitRoute(string $eventClass, string $awaitKey = '')`** and `AwaitRoute::keyOf(IIntegrationEvent): ?string`. One index row of a suspended await. **`Application\Process\IRoutedAwait { routes(): list<AwaitRoute> }`.** **`LongProcess::await_routes(): list<AwaitRoute>`**: the routes while `suspended` (the mechanism's, or `(event_class(), '')`), `[]` otherwise and for a pure alarm. Key rule: a route carries a key only when the mechanism matches by `await_key()`, so the key a fact reports is the key the route stores.
- **`AwaitEvent`** gains optional trailing constructor parameters `?string $await_key = null, int $timeout_seconds = 0, string $on_timeout = AwaitAll::TIMEOUT_FAIL`, the named constructor `AwaitEvent::keyed($class, $key, $criteria = [], $timeout = 0, $on_timeout = fail)`, and `implements IRoutedAwait`. `to_array()` of an unkeyed, alarm-free await is byte-for-byte the 0.6 shape; the new keys appear only when set, and `from_array()` of a 0.6 row is unchanged.
- **`AwaitAll`**: `AwaitAll::keyed($class, list<string|int> $keys, $timeout, $on_timeout)`, the `$key_by` sentinel `AwaitAll::BY_AWAIT_KEY` (= `[IAwaitKeyed::class, 'await_key']`, "the fact's own key"), `is_keyed()`, `implements IRoutedAwait` (keyed: one route per missing key; extractor form: `(class, '')`). The constructor still rejects any other non-callable `key_by`, so a stale extractor still fails decode.
- **`AwaitAny`** (`IAwaitMechanism`, `IRoutedAwait`, `ICancellingAwait`, `IHasDeadline`): `AwaitAny::of(AwaitEvent ...$answers)->cancelledBy(AwaitEvent ...)->until(DateTimeImmutable, $on_timeout)` or `->within(int $seconds, $on_timeout)`. The first accepted branch satisfies it. An answer resumes the next step with that fact. A cancellation compensates, as a FAIL timeout does, with the failure message `Cancelled by <ShortClass>`. `event_class()` is the most specific class or interface that all branch classes share. That value goes in the `waiting_for` column. Not every host matches a fact's parents and interfaces there: mem and pdo do, but `WpdbProcessStore::findWaitingFor`, the wp `ProcessRepository::find_waiting_for` (used by `WpRepositoryProcessStore` and `LegacyProcessStore`) and consumer 0.6 repositories match `waiting_for = class` exactly. So the runner covers it (fix round 1, CR-W4P-6): on a store that does not declare `IMatchesFactAncestry`, it also asks `findWaitingFor()` for each `IIntegrationEvent` ancestor of the fact. `routes()` gives exact rows for a route-indexing store.
- **`ICancellingAwait { cancellation_reason(IIntegrationEvent): ?string }`** is read by the runner after a satisfied `accumulate()`.
- **`IPrecheckAwait { already_satisfied(IAwaitMechanism): ?PrecheckSatisfied }`** (the register's name) is implemented by the `LongProcess` subclass. `PrecheckSatisfied::with($arg)` / `::now()`. Order, under the process lock: the await, alarm and checkpoint commit; the step's commands dispatch; then, unless the row version moved (a fact delivered during the dispatch already took the await), the precheck runs. A hit resumes in place: the alarm is cancelled in the resuming save, and the next step runs in the same wake. It is forward steps only.
- **`ProcessRunner::resume_with_outcome(IIntegrationEvent): ResumeReport`** (`resumed`, `accumulated`, `cancelled` id lists, `isUnheard()`). `resume_on_event()` / `resume()` delegate to it. Lookup for a fact that reports a key: `findWaitingFor(class, key)` ∪ `findWaitingFor(class, '')`. Otherwise `findWaitingFor(class)`. Without `IMatchesFactAncestry` on the store, the fact's `IIntegrationEvent` ancestors are looked up too. `accepts()` filters every candidate. Fan-out rule: see Behaviour change 1.
- **`LongProcess::step_ref(string $purpose = ''): string`** (D3, D13): uuid5 over (process class, process id, current step index, purpose). It is the same on a re-run of the step. Use it as the job id / request ref and as the await key.
- **Why.** TXP D3 (process-kernel; module-map "keyed on a ref the process mints", "register-then-check precheck that absorbs a late fact without FactDeliveredUnheard", "any-of awaits including cancellation facts", "AwaitAll over a checkpointed dynamic key set (children_first)") and register 3.8 / 3.11 (`findWaitingFor(class, key)`).
- **"Without FactDeliveredUnheard".** FactDeliveredUnheard is TXP's signal, not the library's. The library side: a late fact after a satisfied precheck finds no suspended process for its key, and the resume subscriber completes without an error or a retry. `resume_with_outcome()` reports it as unheard by any await, so the host alarm can tell "no await took it" apart from a failure. The library does not remember that a precheck stood in for a specific fact (that needs a store-side absorbed-key index; see Open).

## CR-W4P-2: D7 absolute alarms

- **`IHasDeadline { deadline(): ?DateTimeImmutable }`.** **`AwaitAlarm::at(DateTimeImmutable)`** (kept as ISO UTC) and **`AwaitAlarm::after(int $seconds)`**. `event_class()` is `''`. For an `''` class the runner skips the subscription check and stores `waiting_for = NULL`. `on_timeout()` is `proceed`, and the next step's second parameter receives `null`.
- **Runner.** At suspension the alarm instant is fixed once: the mechanism's `deadline()`, else `now + timeout_seconds()`. The Timeout intent is due exactly then, and the instant is stored in **`ProcessSteps::$await_due_at`** (read with **`LongProcess::await_deadline()`**, cleared when the await ends). Nothing re-delays it: a partial AwaitAll arrival keeps the intent, and the stale-safe timeout wake makes duplicates no-ops. There is no upper bound. The mem test runs a 25 h alarm through a worker restart, the 24h59m59s boundary, a 48 h overshoot and a duplicate wake, and it fires once.
- **Why.** TXP D7 ("absolute-UTC process alarms of 24h or more backed by durable intent rows, with a single-delay conformance test"), scenario `process.alarm-long`.

## CR-W4P-3: step retry policy (D1 inside steps)

- **`#[RetryStep(int $attempts = 0, int $backoff_seconds = 0)]`** on a step method. Without it a failure compensates at once (0.6, the register default "0 → compensate"). With it, a failure runs these steps in one state change: the step method threw or one of its commands threw during dispatch; the step's await is withdrawn if it had suspended (its alarm cancelled); the attempt is counted in **`ProcessSteps::$attempts`** (read with **`LongProcess::step_attempts($step)`**); the process becomes `scheduled` with the step's input payload; a Continue intent with discriminator `retry-{n}` is due after the backoff. The re-run dispatches the same deterministic command ids and mints the same `step_ref()`s, so a D1 effect keyed on them finds its journaled result and does not perform again (tested with `InMemoryEffectJournal`). The process compensates once the retries are used up. Compensation methods are not retried. Each retry is logged at warning. A retried post-await step receives the same second argument (fix round 1, CR-W4P-6): the source of the resume argument is persisted with the retry in **`ProcessSteps::$resume`** and restored by the continuation.
- **Why.** Register 3.8 ("Inside a process step, D1 perform retries follow the step's retry policy (default 0 → compensate); the journal makes a process-level retry of the step reuse the recorded result").

## CR-W4P-4: stranded-process repairs (WP8-10)

- **`Application\Process\Repair\ResumeStrandedProcess(string $consumer_prefix, int $process_id, ?int $expected_version = null)`** and **`FailStrandedProcess(string $consumer_prefix, int $process_id, string $reason, bool $compensate = false, ?int $expected_version = null)`**. Both are `Command` + `ITransactionalCommand`. The handlers are **`ResumeStrandedProcessHandler`** and **`FailStrandedProcessHandler`** (`?IProcessStore, ?IWakeupScheduler, ?IProcessLock, ?IClock, ?ITransactionBoundary`). They fall back to `HostDefaults::for(port, new ConsumerPrefix($prefix))` for the store and scheduler and to `HostDefaults::get()` for the rest; a missing store, scheduler or lock is a `\LogicException`. Refusals throw **`ProcessNotStranded`**.
- **Guards (C23), before any write.** The process lock is taken with a zero wait; held means a worker owns the process, so the repair is refused. The row is re-read under the lock and must be in `findStranded(now)`. With `expected_version`, the row must still be at that version.
- **Resume never runs a step inside the command** (a step dispatches commands, which a command may not). It first fences the row (`touch()` at the guarded version; fix round 1). A `running` row then gets a ResumeRetry intent (`running`, the row's step and the fenced version, due now); a `scheduled` row gets a Continue intent. Both carry a `repair-<UTC time>` nonce. The drain re-runs the step with its deterministic command ids. This is the mechanism `process.crash-mid-step` already uses (W3CP note).
- **Fail.** Without `compensate`, a fenced save makes the row `failed` with "Failed by operator: <reason>". With `compensate`, the row enters compensation (completed steps undone in reverse; the stranded step itself is not compensated) and becomes `scheduled` with a Continue intent (`undo-repair-<time>`), and the drain ends it `failed`.
- **Why.** Register 3.10 / 5.3 step 5, WP8-10 ruling. The operator view already names the repairs `resume_stranded` and `fail_stranded`.

## CR-W4P-5: D10 workflow ignition ledger port

- **`Application\BehaviourWorkflows\IWorkflowIgnitionLedger`**: `claim(string $dedupKey, string $kind, ?string $eventId = null): bool`, `attach(string $dedupKey, int $workflowId): void`, `find(string $dedupKey): ?WorkflowIgnition`, `release(string $dedupKey): void`. It is the shape of ddd-symfony's `DbalWorkflowIgnitionLedger`, except that `find()` returns the value object **`WorkflowIgnition(dedupKey, kind, ?workflowId, ?eventId, createdAt)`** instead of an array.
- **`IStartsFromFact`**: `workflow_kind()`, `workflow_from_fact(IIntegrationEvent): ?BehaviourWorkflow`, `ignition_key(IIntegrationEvent, string $eventId): string` (`''` = no dedup), `save_ignited(BehaviourWorkflow)` (inside the ignition transaction), `start_ignited(BehaviourWorkflow)` (after commit). The workflow class declares its facts with the existing `#[StartsOn]` attribute. **`StartsFromFacts`** trait for `WorkflowHandler` subclasses: kind = the class, key = `uuid5(event_id, kind)`, save through `workflow_repo`, start = `handle_workflow()`.
- **`WorkflowIgniter(IWorkflowIgnitionLedger, ?ITransactionBoundary = null, ?LoggerInterface = null)`.**
  - `register(IStartsFromFact, ISubscriptionRegistry, string $consumerPrefix)` adds one `Subscriber::IGNITION` subscriber per `#[StartsOn]` fact, id `{prefix}/workflow-ignition:{class}@{fact}`. It refuses a class without `#[StartsOn]`.
  - `ignite()` returns **`WorkflowIgnitionResult(outcome, ?dedupKey, ?workflowId, ?startError)`** with **`WorkflowIgnitionOutcome`** `Ignited | AlreadyIgnited | Declined`.
  - Claim, save and attach run in one `ITransactionBoundary::run` (joined if open), so a failed save releases the key. Without a boundary the claim is `release()`d explicitly.
  - The loser of a claim is told the winner's workflow id.
  - A `start_ignited()` failure after commit is logged at error and returned in `startError`; the single ignition stands. Superseded in fix round 1 (CR-W4P-6): the subscriber rethrows the start error, and a later ignition with the key restarts the workflow.
- **`WorkflowIgnitionKey::forFact($eventId, $kind)`** (= sf `keyForFact`) and **`::perMinute($scope, $at)`** (`{scope}:{Y-m-d\TH:i}Z`, UTC). TXP's "(workflow, minute)" key is `perMinute(kind . ':' . entry, due_at)`.
- **Why.** Register 3.11 D10, ruling #78, scenario `workflow.fact-ignition-once` (mem and sf, wave 4). The test covers the same fact twice, two ticks in one minute, and the next minute.

## CR-W4P-6: fix round 1

All additive; review findings of round 1 in brackets.

- **[major] A retried post-await step keeps its fact.** New `ProcessSteps::$resume` (`?array`, trailing constructor parameter, default `null`; JSON key `resume`), `LongProcess::resume_source()` / `set_resume_source()` (`@internal`), and the `@internal` codec `Application\Process\ResumeSource`. When `#[RetryStep]` schedules the re-run of a resumed step, or an `#[Async]` post-await step defers to its continuation, the runner stores where the argument came from: the satisfied mechanism (`to_array()`) plus the fact (`integration_payload()`), or the precheck's own value (an event, a `JsonLifecycleValue`, or plain scalars). The entry is stamped with the step index. `continue_scheduled()` rebuilds the argument (`from_array()` then `resume_argument($fact)`, or `from_payload()`), so the re-run receives the same fact, or the same AwaitAll tally. The entry is cleared when the step completes, when a new await suspends and on compensation. A precheck value that cannot be persisted (an object that is neither an event nor a `JsonLifecycleValue`) is logged at error, and the step is not retried: it compensates. Tests: a non-nullable `JobFinished` post-await step that fails once and is retried on a fresh runner; a post-gather retry; an `#[Async]` post-await step.
- **[major] AwaitAny on exact-match stores.** New marker `Runtime\Process\IMatchesFactAncestry`. A store declares it when its `findWaitingFor($class)` also returns rows waiting for a parent or interface of `$class`. Without the marker, `ProcessRunner::candidates()` also calls `findWaitingFor($ancestor)` for every parent class and interface of the fact that is an `IIntegrationEvent` type, so an AwaitAny row (its `waiting_for` holds the branches' common ancestor) is found on wp, on `LegacyProcessStore` and on consumer repositories. This costs a few extra prefilter lookups per fact until a store declares the marker. It also fixes the 0.6 case of an `AwaitEvent` on a parent class, which never resumed on an exact-match store. The `IProcessStore` and `AwaitAny` docblocks are corrected. Test: `CancellableSyncProcess` through `LegacyProcessStore(ArrayProcessRepository)`, both the answer and the cancellation branch.
- **[major] D10 recovery of a failed start.**
  - The subscriber that `WorkflowIgniter::register()` adds now rethrows `startError`, so the delivery ledger records a failed attempt and redelivers.
  - The start is gated by a **start marker**, a second entry in the same ledger under `WorkflowIgnitionKey::startMarker($dedupKey)` (new; uuid5 under the fixed `WorkflowIgnitionKey::START_NAMESPACE`). The marker is claimed after the ignition commits, right before `start_ignited()`, and released when the start throws.
  - Any later ignition with the key (the delivery's retry, or another fact such as the next tick in the same minute) finds the workflow attached and no marker. It claims the marker, loads the workflow and starts it if `is_active()`. That is the new outcome **`WorkflowIgnitionOutcome::Restarted`**.
  - The load goes through the new optional interface **`ILoadsIgnitedWorkflow { load_ignited(int): ?BehaviourWorkflow }`**. The `StartsFromFacts` trait provides `load_ignited()` (through `workflow_repo->get_by_id()`), and the igniter accepts the method with or without the interface. A class with neither is logged at error and not restarted.
  - Because the marker claim is the gate, exactly one caller starts the workflow. Residual: a worker that dies inside `start_ignited()` keeps the marker, and an operator `release()`s it.
  - Tests: a start that fails once, its redelivery through a shared delivery ledger, a third delivery and a second tick, after which the workflow has started exactly once; and a restart by a later tick.
- **[minor] Stale claims without a boundary.** `WorkflowIgniter` gains optional trailing parameters `?IClock $clock = null, int $stale_claim_seconds = 900`. Without a transaction boundary, a claimed key with `workflowId === null` older than the threshold is released and claimed again (logged at warning). A younger one is reported `AlreadyIgnited` with no workflow id. With a boundary nothing is reclaimed. Residual: two reclaimers racing on the same stale key at the same instant can both win, because there is no boundary to serialise them. Test included.
- **[minor] Fan-out vs 0.6 first-wins (R1).** See Behaviour change 1. Keyed awaits and AwaitAny fan out. Unkeyed AwaitEvent, extractor AwaitAll and consumer mechanisms keep 0.6 first-wins. Test: two processes on an unkeyed `AwaitEvent(UserJoined)`, where one fact resumes only the first and the next fact resumes the second. **Coordinator: please ratify this rule** (it narrows the round-0 fan-out to the wave-4 mechanisms).
- **[minor] Repair lock window.** `ITransactionBoundary` has no after-commit hook, and nesting `run()` inside the command's transaction is rejected, so the lock cannot be held through the outer commit. Instead `ResumeStrandedProcessHandler` fences the row first (`touch()` at the guarded version) and its ResumeRetry intent carries the fenced version. A worker that takes the lock in the window and acts on the pre-repair row loses its fenced write. `FailStrandedProcessHandler` already saved fenced. The residual window (non-fencing `LegacyProcessStore`) is documented in `StrandedRepair`, and the repair's intents stay stale-safe there. Test: the repair inside an open boundary, followed by a pre-repair save, which gets `ConcurrentProcessModification`.

## Behaviour changes (no signature change)

1. **Fan-out of a fact (amended in fix round 1).** A keyed await (`AwaitEvent::keyed`, `AwaitAll::keyed`) or an `AwaitAny` takes the fact in every suspended process that accepts it, in id order. A cancellation fact (an app's destruction) must reach every process it cancels, and a keyed answer reaches only the process that minted the key. A 0.6-shaped await (unkeyed `AwaitEvent`, extractor-keyed `AwaitAll`, any consumer mechanism) keeps 0.6/wave-3 first-wins: once one of them took the fact, no other 0.6-shaped await takes it. Existing 0.6 consumers (cred) see no change. A contended lock on one candidate still throws, the delivery retries the resume subscriber, and processes already resumed are no longer suspended (stale-safe).
2. **A suspending forward step's checkpoint is persisted with its await.** Before, `Result::$checkpoint` of a suspending step was dropped, so its compensation received `null`. A process that relied on a `null` checkpoint there now receives the value its step returned.
3. **`waiting_for` of an AwaitAny** is the branches' common class or interface (for example `IntegrationEvent`), and that of an `AwaitAlarm` is `NULL`. Unchanged for every 0.6/wave-3 mechanism.
4. **`resume_argument` is cleared when `run()` ends** (it could leak from a precheck or an empty gather into the next wake of a long-lived runner).
5. **A keyed AwaitAll ignores a fact that reports no key.** The extractor form is unchanged.

## Compatibility impact

- **R2:** no constructor changed shape. `AwaitEvent` and `AwaitAll` positional calls are unchanged. New `ProcessSteps` constructor parameters are trailing with defaults. `WorkflowHandler` is unchanged (the trait is opt-in).
- **Persisted rows:** new state lives in existing JSON columns (`steps` gains `attempts`, `await_due_at` and, in fix round 1, `resume`; the start markers are ordinary ignition-ledger rows; new mechanisms serialise through `to_array()`), so no schema change on any host. Old rows decode unchanged (tested).
- **Rollback to 0.6.x / a wave-3 build (register 7.3):** a row suspended on `AwaitAny`, `AwaitAlarm` or a keyed `AwaitEvent` written by this branch is not understood by older code. An unknown mechanism class fails to decode there. A keyed `AwaitEvent` decodes, but without its key, so on 0.6 it would accept any fact of the class that matches the criteria. Rollback guidance: drain or finish such processes before a rollback; wp should not use the new mechanisms until its rollback fixtures cover them. `ProcessSteps` rows with the new keys are read by 0.6 (it ignores unknown keys).

## Open

- The library does not record which late fact a precheck absorbed (see CR-W4P-1). If TXP wants FactDeliveredUnheard to stay quiet for a late *keyed* fact while the same class has other live awaits, the precise form is an absorbed-route row per satisfied precheck (a store change). `ResumeReport::isUnheard()` is the hook available now.
- `IPrecheckAwait` is implemented by the process. A container-provided precheck service (`IAwaitPrechecker` resolved through `HostDefaults`) would let Symfony inject the query bus. It can be added later as an optional runner argument.
- `tests/Unit/Process/ProcessLockAcquisitionTest` still pins the hotfix half of `lock.contention` on the transitional AS scheduler (W3-WPC3-1 says it can point at the v8 scheduler). Not changed here; the wp v8 conformance already pins the re-queue.

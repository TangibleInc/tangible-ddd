# Domain classes may build themselves from DTOs

DDD-L1 kept the domain from referencing anything in the Application layer, yet the framework ships `IDTOConstructible`, a domain contract whose `from_dto()` takes the Application `IDataTransferObject`, and Tangible Cred builds sixteen of its domain classes that way. A developer following the rule as written moved the mapping into a command handler instead, which left the handler holding a factory for every nested value object and the codebase with two ways to do one thing. The rule had two jobs under one heading. Keeping the domain free of WordPress, I/O, and persistence is what makes it testable without a database, and that stays absolute. Keeping it free of Application types only protects the direction of dependency, and a DTO is a plain data class, so a domain class that reads one stays testable. DDD-L1 therefore names one exception, the DTO factory: a static `from_dto()` (and its list forms) that reads a DTO's fields and calls constructors, and nothing else. The accepted cost is that a change to a DTO's fields changes the factory reading it; the mapping sits beside the invariants it feeds, which is where a reader looks for it. Rejected: mapping in the handler, which spreads one aggregate's construction across every handler that builds it; a `to_domain()` method on the DTO, which keeps the dependency one way but makes the DTO the place that knows how the aggregate is assembled; a mapper class per aggregate, the same with one more file; leaving the rule unchanged and recording each factory in a Phan baseline, which turns a sanctioned pattern into a list of excuses.

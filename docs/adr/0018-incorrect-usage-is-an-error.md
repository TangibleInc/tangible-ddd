# A programming error is an `\Error`, never an `\Exception`

Every error the framework throws because code is wired or used wrong extends `TangibleDDD\IncorrectUsage`, which extends `\Error`. That covers nested dispatch, a raise past the seal, a missing self-handling `handle()`, an unregistered await, a misdeclared `#[Touches]`, and the rest. Before 0.6.12 these were spread across `ApplicationException`, `\LogicException` and `\DomainException`, all of them `\Exception`s, so the usual WordPress `catch (\Exception)` around a hook callback swallowed them into a log line. A command dispatched from a hook inside another command then vanished: the guard threw, the hook caught it, and nothing failed. As an `\Error` it passes through those catches and fails the request; only a deliberate `catch (\Throwable)` or `catch (IncorrectUsage)` stops it. Domain rules stay `InvariantException` and runtime or infrastructure failures stay `\Exception`, because both are recoverable at the edge of an operation (`WorkflowHandler` catches `InvariantException` to fail a workflow). An absent plugin (`NoConsumerOwnsClass`) is likewise a runtime condition, which `IntegrationHookName` tolerates by design (0.6.6). Misuse belongs to no layer, so the class sits at the framework root, and DDD-L1 names it as a dependency the domain may take. Rejected: placing it in `Domain\Exceptions` beside `InvariantException`, which satisfied DDD-L1 without changing it but read as if misuse were a domain concept; a `Kernel` namespace holding one class; reusing `InvariantException` (it is caught on purpose, and it means a domain rule, not misuse); `\LogicException` (still an `\Exception`); keeping misuse under `ApplicationException` (the same). `Infra\Exceptions\IncorrectUsageException` remains as a deprecated subclass so existing catches keep matching.

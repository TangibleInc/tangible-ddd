# A command sent from foreign code inside an act is captured only in a declared window, and every capture is decided before the act ends

An act never nests (DDD-M1): a command sent while one is open throws `CommandDispatchedInsideCommand`, an `IncorrectUsage` ([ADR 0018](0018-incorrect-usage-is-an-error.md)). That is right for our own code, but a handler sometimes has to call foreign code that sends a command through a WordPress hook the handler doesn't own. Cred's bulk issue is the case: completing a LearnDash course inside a workflow item fires `learndash_course_completed`, and Cred's own completion hook sends `IssueCompletionEarningsCommand`, which the bulk run is already issuing itself, with its own origin and date. So a handler may wrap such a call in `Intents::capture()`, which opens a **window**. A command sent inside the window is not run and does not throw; `CorrelationMiddleware`'s guard captures it as an **intent** (the command, its trace context, and the sender's file:line), and the sender gets `null`, as from any void handler. The handler then **decides** each one: `fulfil()` (the act does the work in-band itself) or `reject($reason)`. `IntentsMiddleware`, between `TransactionMiddleware` and `DomainEventsPublishMiddleware`, fails the act with `UndecidedIntents` if any intent is left undecided, inside the transaction, so a transactional act rolls back. The decisions are recorded on the act's audit row, in a new `command_audit.intents` column (schema v8). Outside a window nothing changes: a nested send still throws, and so does a non-`ICommand` message sent inside one. The window is declared, never inferred, so every exception to DDD-M1 is visible in the handler's code and in the audit. Rejected: unhooking the listeners around the call (invisible in the audit, and it silently drops whatever else the foreign code sends); silently dropping nested sends (the same loss, made general); queueing them automatically to run later (that is the planned third decision, **defer**, and only ever by decision; it needs command serialization, which does not exist yet); recording intents in the audit's `events` column (the dashboard reads that column as the act's moments and would draw intents as events). Concept and usage: [captured intents](../intents.md).
